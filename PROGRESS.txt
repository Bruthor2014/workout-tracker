WORKOUT TRACKER — ESTADO DO PROJETO
Última atualização: 2026-10-14

Este ficheiro existe para continuidade entre máquinas/sessões — a conversa
com o Claude e a memória local dele ficam presas a cada computador. Isto
viaja com o projeto (git). NOTA IMPORTANTE: este projeto já foi trabalhado
em duas máquinas diferentes, por duas sessões de Claude Code separadas sem

======================================================================
STACK E BASE
======================================================================
- Backend: Node.js + Express 5, PostgreSQL (SQL direto via `pg`, sem ORM)
- Frontend: React 19 + Vite, React Router 7 (lazy-loaded por página)
- Auth: JWT + bcrypt, role-based access control
- Projeto no GitHub: https://github.com/Bruthor2014/workout-tracker

======================================================================
ROLES (importante — já mudou duas vezes)
======================================================================
- `member`            — utilizador normal, treina
- `personal_trainer`, `nutritionist` — staff especializado
- `receptionist`       — gestão do dia-a-dia (presenças, membros)
- `intern`             — staff em formação (pouca funcionalidade própria)
- `gym_owner`          — "CEO": gere UM ginásio (equipa, finanças, horários,
                          tema). Conta de gestão — NÃO tem treinos/planos
                          próprios (bloqueado por middleware `notOwner`).
- `dono`               — dono da PLATAFORMA (não de um ginásio específico).
                          Mais recente, pouco testado ainda.
- `admin`              — reservado, ainda sem uso real (pode ter sido
                          substituído pelo conceito de `dono` — verificar).

gym_id em `users` já é NULLABLE (clientes externos/dono não pertencem a
nenhum ginásio) — isto era a "Fase A" que estava planeada, já foi feita.

======================================================================
FUNCIONALIDADES — o que existe hoje (alto nível; há MUITO mais detalhe no
código do que cabe aqui, sobretudo no bloco construído em 2026-10-14)
======================================================================

MEMBRO (uso pessoal)
- Planos de treino multi-dia, planos de nutrição (refeição->opção->itens)
- Composição corporal com gráficos de evolução
- Treinos em direto (cronómetro) ou manuais
- Dashboard: calendário semanal, estatísticas reais, progresso mensal
- Seletor de exercícios com pesquisa + filtro por grupo muscular + imagem
  real por exercício (catálogo com 100+ exercícios agora, incl. Cardio)
- Mensagens diretas

GESTÃO DE GINÁSIO (gym_owner/"CEO") — construído numa sessão separada,
pouco testado por mim ainda:
- Painel "Gestão" (/management): membros, ativos/inativos, treinos da
  semana, aulas de grupo, gráfico de treinos por semana, gestão de equipa,
  tema de cor personalizado do ginásio (aplicado a todos os utilizadores
  desse ginásio)
- Membros: pesquisa, filtro de inativos, adicionar pessoa, mensagens
  globais/segmentadas com placeholder {nome}
- Aulas de grupo (/classes): horário semanal, aulas/palestras/eventos,
  confirmação em duas partes (instrutor + receção), cancelamento
  automático se faltarem inscritos, substituições
- Horários da equipa (/team-schedule): turnos semanais, gerador automático
  de horário, vista por pessoa ou toda a equipa
- Ocupação (/occupancy): check-ins em tempo real
- Financeiro (/finance ou aba "Financeiro"): salário base + taxas por
  tipo de trabalho (receção/sala/aula) + taxa mensal por cliente de PT,
  retenção do ginásio (% ou fixo), confirmação semanal de horas
- Presenças da equipa (staff_attendance) — ver bug encontrado abaixo
- Clientes externos de PT/nutricionista (fora do ginásio, via código de
  convite — `invite_code` em users, tabela `external_coach_clients`)

SUBSCRIÇÕES
- personal_training, nutrition_plan, gym_membership — cada uma
  ativa/inativa, com staff atribuído quando aplicável

======================================================================
BUGS REAIS ENCONTRADOS E CORRIGIDOS (cronológico, os dois blocos juntos)
======================================================================
- Modal (editar subscrição, etc.) aparecia confinado/transparente quando
  aberto de dentro de um cartão com `backdrop-filter` — corrigido com
  `createPortal` para `document.body` em Modal.jsx
- GlassCard.jsx não aceitava a prop `style` (ajustes de espaçamento
  silenciosamente sem efeito nalgumas páginas)
- `toDateKey()` convertia para UTC antes de formatar — desalinhava
  calendário/estatísticas em fusos horários != UTC+0 (ex: Portugal)
- JWT expira ao fim de 7 dias e a app ficava presa a mostrar "Token
  inválido ou expirado" sem opção de recuperação — agora `apiRequest`
  limpa a sessão e redireciona para /login automaticamente num 401
- 2026-10-14, ao sincronizar as duas máquinas: a tabela `staff_attendance`
  era usada por vários controllers (attendanceController, classController,
  financeController) mas o CREATE TABLE tinha ficado só na BD viva da
  outra máquina — nunca chegou ao schema.sql nem às migrations.
  Reconstruída a partir do código e adicionada ao schema.sql.
- 2026-10-14: `class_cancellations.reason` só permitia
  ('not_enough','no_instructor') mas o cancelamento manual insere 'manual'
  — ia rebentar com violação de constraint na primeira vez que alguém
  cancelasse uma aula à mão. Constraint alargada.

======================================================================
BASE DE DADOS — COMO FICAR ATUALIZADO NUMA MÁQUINA NOVA/ANTIGA
======================================================================
Além do schema.sql, existem migrations incrementais em
backend/db/migrations/001...018 — todas escritas de forma defensiva
(IF NOT EXISTS / IF EXISTS), seguras de correr mais que uma vez ou numa
BD que já tenha parte das alterações feitas à mão. Se abrires este
projeto numa BD desatualizada:

  cd backend/db/migrations
  for f in *.sql; do
    psql -U postgres -d workout_tracker -v ON_ERROR_STOP=1 -f "$f"
  done

Se isso falhar com "relation X does not exist", é sinal de que falta algo
no schema.sql que só existia numa BD viva de outra máquina (já aconteceu
uma vez com staff_attendance, acima) — procurar no código como essa tabela
é usada e reconstruir, como fiz para staff_attendance.
