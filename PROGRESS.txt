======================================================================
STACK E BASE
======================================================================
- Backend: Node.js + Express 5, PostgreSQL (SQL direto via `pg`, sem ORM)
- Frontend: React 19 + Vite, React Router 7 (lazy-loaded por página)
- Auth: JWT + bcrypt, role-based access control
- Projeto no GitHub: https://github.com/Bruthor2014/workout-tracker
- Supabase: existe um projeto Supabase (Postgres gerido), agora a BASE DE
  DADOS DE PRODUÇÃO a sério (ver secção PRODUÇÃO abaixo) — já não é só
  "pensado como futura". A BD local continua uma cópia em Postgres normal,
  separada.

ROLES (já mudou três vezes — ver com atenção, sobretudo os dois novos)
======================================================================
- `member`            — utilizador normal, treina
- `personal_trainer`, `nutritionist` — staff especializado, com clientes
- `receptionist`       — PESSOA normal da equipa (como um PT): treina,
                          tem planos próprios, E faz tarefas de balcão
                          (ocupação, membros, presenças da equipa). Pode
                          alternar na sidebar entre modo "Pessoal" e
                          "Profissional" (ver secção SIDEBAR abaixo).
                          NÃO tem acesso a "Horário da equipa" (isso é
                          só do gym_owner — a página nem funcionava para
                          ela, usava endpoints só-CEO).
- `reception_station`  — NOVO (2026-10-16). Conta do PC fixo do balcão —
                          NÃO é uma pessoa, não treina, não tem planos
                          próprios (bloqueada por `notOwner`, tal como o
                          gym_owner/dono). Permissões: Membros (ver/criar/
                          gerir subscrições — "mudar planos dos membros"),
                          Ocupação (registar entradas/saídas), Aulas de
                          grupo (ver + confirmar presença de PTs, tal como
                          a rececionista), Horário da equipa (só vê, não
                          edita), Mensagens.
- `intern`             — staff em formação (pouca funcionalidade própria)
- `gym_owner`          — "CEO": gere UM ginásio (equipa, finanças,
                          horários, tema). Conta de gestão — NÃO tem
                          treinos/planos próprios (bloqueado por `notOwner`).
- `dono`               — dono da PLATAFORMA (não de um ginásio específico).
                          Gere todos os ginásios, pode mudar role/gym_id de
                          qualquer utilizador (painel /dono).
- `admin`              — reservado, ainda sem uso real.

gym_id em `users` é NULLABLE (clientes externos/dono não pertencem a
nenhum ginásio).

======================================================================
SIDEBAR — modo Pessoal / Profissional (2026-10-16)
======================================================================
Staff que é também pessoa (personal_trainer, nutritionist, receptionist,
intern) tem um interruptor no topo da sidebar para alternar entre:
- Pessoal: Planos de Treino, Planos de Nutrição, Os teus treinos,
  Registar treino, Aulas de grupo — tal como um membro normal.
- Profissional: Clientes (só PT/Nutri), Aulas de grupo, O meu horário,
  Membros, Equipa, e para a rececionista especificamente também Ocupação
  e Presenças Staff.
A escolha fica guardada por conta em localStorage (`sidebarMode:<id>`).
gym_owner, dono e reception_station NÃO têm este interruptor — são contas
de gestão/estação, sem modo pessoal.

FUNCIONALIDADES — o que existe hoje (alto nível)
======================================================================

MEMBRO (uso pessoal)
- Planos de treino multi-dia, planos de nutrição (refeição->opção->itens)
- Plano de treino: cada exercício tem técnica (normal/drop set/rest-pause/
  cluster/super-set/pirâmide/até à falha — migration 028, `set_type`) E
  uma linha por SÉRIE planeada com o seu próprio alvo de reps/carga
  (migration 029, tabela `plan_exercise_sets` — já não é um valor só para
  todas as séries, dá para variar, ex: pirâmide). O recorde pessoal
  (GET /sessions/records) aparece junto de cada exercício no editor do
  plano. Ao iniciar um treino a partir de um dia do plano, a técnica e o
  alvo de cada série já vêm pré-preenchidos.
- Composição corporal com gráficos de evolução
- Treinos em direto (cronómetro) ou manuais
- Dashboard: calendário semanal, estatísticas reais, progresso mensal
- Seletor de exercícios com pesquisa + filtro por grupo muscular + imagem
  real por exercício (catálogo com ~200 exercícios, incl. Cardio) +
  exercícios PESSOAIS criados pelo próprio (owner_id, migration 024 — só
  visíveis para quem os criou, nunca entram no catálogo do ginásio)
- Mensagens diretas — já dá para pesquisar contactos por nome OU email
- Amigos/seguidores (migration 023): seguir é direto, sem aprovação;
  FriendsPage lista seguidores/a seguir, FriendComparePage compara
  estatísticas de treino com um amigo
- O Teu Financeiro (MyFinancePage): membro vê o estado das suas próprias
  subscrições/pagamentos, sem precisar de ser staff

GESTÃO DE GINÁSIO (gym_owner/"CEO")
- Painel "Gestão" (/management): membros, ativos/inativos, treinos da
  semana, aulas de grupo, gráfico de treinos por semana, gestão de equipa,
  tema do ginásio (ver secção TEMA abaixo)
- Membros: pesquisa por nome/email, filtro de inativos, adicionar pessoa,
  mensagens globais/segmentadas com placeholder {nome}
- Aulas de grupo (/classes): horário semanal, aulas/palestras/eventos,
  confirmação em duas partes (instrutor + receção — agora também a conta
  "Receção"), cancelamento automático se faltarem inscritos, substituições
- Horários da equipa (/team-schedule): turnos semanais, gerador automático
  de horário — gym_owner edita; receção só vê (sem botões de criar/editar/
  remover, sem conseguir clicar nos turnos)
- Ocupação (/occupancy): registo de entrada/saída agora por PESQUISA DE
  EMAIL (não carrega a lista toda de membros — pensado para ginásios
  grandes, não só os de teste)
- Financeiro (/finance): salário base + taxas por tipo de trabalho +
  taxa mensal por cliente de PT, retenção do ginásio, confirmação semanal
- Presenças da equipa (staff_attendance)
- Clientes externos de PT/nutricionista (via `invite_code` + tabela
  `external_coach_clients`)

SUBSCRIÇÕES
- personal_training, nutrition_plan, gym_membership — cada uma
  ativa/inativa, com staff atribuído quando aplicável. Quem gere: CEO,
  rececionista E agora também a conta "Receção".

TEMA DO GINÁSIO (2026-10-16, reescrito de propósito)
- O CEO escolhe DUAS cores (principal + secundária) em vez de uma só com
  tons derivados — era "confuso" na versão antiga.
- As duas cores aplicam-se a TODA a app para quem está no ginásio:
  botões/links/destaques (principal), fundo da página, sidebar, cartões,
  modais, popovers/dropdowns, tooltips de gráficos, calendário de
  horários/aulas (secundária, sempre suavizada em saturação/luminosidade
  para não ficar garrido com cores muito vivas).
- A imagem de fundo fixa (background.webp) é substituída por um gradiente
  nas duas cores quando há tema; sem tema, mantém-se a imagem original.
- Guardado em `gyms.accent_color` / `gyms.secondary_color`, propagado no
  login como `gym_accent`/`gym_secondary` no payload do user.
- Implementação: `frontend/src/utils/theme.js` deriva tudo via HSL a
  partir das duas cores e escreve custom properties CSS no `:root`
  (--accent, --accent-strong, --accent-deep, --accent-light, as versões
  *-rgb de cada uma, --surface-rgb/--surface-strong-rgb para fundos
  neutros, --bg-base, --glass-bg(-strong), --glass-border, --bg-image).
- IMPORTANTE (2026-10-21): o tema POR OMISSÃO (sem gym_owner ter escolhido
  cores) deixou de ser o roxo/glassmorphism original — passou a um visual
  "grafite + lima" achatado (sem gradientes/glow, raios de canto
  pequenos), definido em `frontend/src/index.css` `:root`. Isto é só a
  BASE; o mecanismo de tema por ginásio (acima) continua a funcionar
  exatamente na mesma por cima, via as mesmas custom properties — um CEO
  que escolha cores próprias continua a sobrepor-se ao grafite+lima. Já
  em produção, não é só uma experiência local.

BASE DE DADOS
======================================================================
Migrations incrementais em backend/db/migrations/001...029 — todas
escritas de forma defensiva (IF NOT EXISTS / IF EXISTS), seguras de
correr mais que uma vez. Correr uma migration nova em AMBAS as bases —
local (via o loop abaixo, ou um script node com `pg` direto) E produção
(Supabase — buscar a connection string em Secret Manager:
`gcloud secrets versions access latest --secret=database-url`, já com o
PATH do gcloud tratado na secção PRODUÇÃO). Sem isto o código novo
funciona em local e rebenta em produção (coluna/tabela em falta).
`backend/db/supabase_setup.sql` é o ficheiro combinado (schema + replay
de todas as migrations) para colar de uma vez no SQL editor do Supabase
— mantém sincronizado sempre que mexeres numa tabela: o CREATE TABLE
base NUNCA deve ganhar colunas que uma migration posterior ainda espera
remover/migrar (ver migration 029 para um exemplo — o CREATE TABLE base
de `plan_exercises` manteve as colunas antigas, só a migration no fim do
ficheiro é que as migra e remove).

Se abrires este projeto numa BD desatualizada:

  cd backend/db/migrations
  for f in *.sql; do
    psql -U postgres -d workout_tracker -v ON_ERROR_STOP=1 -f "$f"
  done

Se isso falhar com "relation X does not exist" ou "column X does not
exist", é sinal de que falta algo no schema.sql que só existia numa BD
viva de outra máquina — procurar no código como é usado e reconstruir
(já aconteceu com staff_attendance e com accent_color/secondary_color).

POR FAZER / EM ABERTO
======================================================================
- CORRIGIDO (2026-10-20): requireAuth (middleware/auth.js) confiava em
  gymId/role guardados no JWT no momento do login, válidos por 7 dias —
  mas gym_id/role podem mudar entretanto (ex: o DONO atribui alguém como
  CEO de um ginásio novo). Quem tivesse sessão aberta de antes da mudança
  escrevia no ginásio ERRADO em qualquer endpoint que confiasse em
  req.user.gymId, sem erro nenhum (ex: updateTheme alterou as cores de
  outro ginásio). requireAuth agora confirma sempre gymId/role na BD a
  cada pedido, nunca só do token — corrige isto para toda a app de uma
  vez. Reproduzido, corrigido e verificado em local; mesma correção já
  publicada em produção.
- ATUALIZADO (2026-10-21): registo em duas fases (migration 027) —
  confirmação de email e login/registo com Google (authController.js
  register/verifyEmail/resendVerification/googleAuth, services/email.js,
  routes/authRoutes.js; frontend: RegisterPage/LoginPage/VerifyEmailPage/
  GoogleSignInButton). Estado atual:
    - Google: CONFIGURADO e ATIVO, local e em produção (GOOGLE_CLIENT_ID/
      VITE_GOOGLE_CLIENT_ID definidos, domínio ironbound.pt autorizado nas
      Authorized JavaScript origins). Login com Google cria conta logo
      com `is_new`, pede o nome antes de avançar (GoogleSignInButton.jsx,
      ConfirmNameStep).
    - Email: AINDA sem SMTP configurado (sem SMTP_HOST/SMTP_USER/SMTP_PASS
      no .env), tanto local como em produção. O link de confirmação só
      existe no log do servidor (Cloud Run em produção) e, em dev, vem na
      resposta da API em `dev_verification_link`. Ver backend/.env.example
      para como ligar um SMTP a sério (Gmail precisa de "App Password").
  Contas antigas (antes desta migração) ficam com email_verified=true por
  omissão — só quem se regista agora pelo formulário normal (sem Google)
  nasce por confirmar.
- EM ABERTO (2026-10-25): app Android via Capacitor, para gerar um .apk
  a sério. `frontend/android/` já está montado (`npx cap add android`,
  `capacitor.config.json` com appId `pt.ironbound.app`, aponta para a API
  de produção via `.env.production`), scripts `npm run android:sync` /
  `npm run android:open` no frontend/package.json. BLOQUEADO: esta
  máquina não tem Android Studio nem Android SDK instalados (só um JDK
  1.8 muito antigo — é preciso um JDK 17+). O disco C: só tem ~1.7 GB
  livres (D: tem ~417 GB) — ao instalar o Android Studio, É PRECISO
  escolher uma pasta no D: (tanto para o próprio Android Studio como
  para o Android SDK no assistente de primeira abertura), senão a
  instalação falha por falta de espaço. Depois de instalado, o resto
  (gerar o .apk) é rápido — Build > Build Bundle(s)/APK(s) no Android
  Studio, ou `gradlew assembleDebug` por linha de comandos.
- IMPORTANTE: preço das subscrições (gym_service_prices, migration 025) é

  igual para todos os membros. No mundo real, membros diferentes podem ter
